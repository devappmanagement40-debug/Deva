name: Global USDT deposit policy
description: Deposits are crypto USDT only; remove Mobile Money and automatic XOF/USDT conversion while preserving historical records.
---

All countries use USDT for new account activity. The user explicitly wants Mobile Money deposit methods removed and the automatic XOF/USDT conversion rate no longer used. Keep USDT crypto deposits as the deposit method. Do not delete old Mobile Money records or historical XOF transactions; preserve them for audit. Legacy XOF account balances require an exact admin-entered USDT credit per account, with explicit confirmation before applying it. For new deposits, the USDT amount entered is the full amount credited to the member; DIAMANT absorbs processor fees. Quotes for other supported crypto assets must represent that entered USDT value. Disclose that wallet/network gas fees are separate and charged in the network's native asset. Customer and admin deposit screens must refer to the processor generically, never by name. The chosen flow starts with instrument selection, then asks for the USDT amount, and creates an amount-specific payment request with an exact transfer quote and network instructions. Do not describe it as a permanent address for arbitrary amounts.

An administrator may manually approve a pending/review crypto USDT deposit only after independently verifying the exact on-chain transaction. Require an explicit acknowledgement and transaction hash, persist the hash uniquely for reuse prevention, and credit the USDT wallet atomically exactly once. The member-facing validation button only checks payment status; it must never force a credit.

**Why:** the user now wants a site-wide USDT account currency and later superseded the earlier request to keep CI/Togo Mobile Money, explicitly asking to remove Mobile Money and the conversion rate. The user confirmed that a deposit amount such as 300 USDT must credit 300 USDT, with processing fees borne by DIAMANT, and requested that deposit pages not name the processor. The provider’s direct USDT-to-network-USDT estimate fails even when those currencies are enabled; USD works as the internal quote currency, and explicit pay amounts are needed for stablecoin instruments to keep the member’s requested transfer amount exact. Although a permanent-address/free-amount flow was discussed, the user then chose to keep the current payment integration, so each request must continue to use its exact quoted amount rather than implying arbitrary transfers to a permanent address. The user later explicitly chose admin-only manual crypto approval after being warned that it can credit a payment not automatically confirmed.

**How to apply:** Disable Mobile Money deposits in both UI and server routes; accept deposits in USDT crypto only. Keep legacy Mobile Money deposit records unchanged. Add a protected admin workflow for manual legacy-balance credits; never infer an exchange rate or silently map an XOF amount to USDT. Start deposits with instrument selection, validate the amount against current settings, then create the existing amount-specific payment only after the member confirms the selected instrument and amount. Use USD only as the provider’s internal quote currency; never display it as the member’s deposit currency. Set the provider pay amount to the entered value for USDT, USDC, and PYUSD instruments; let the provider quote volatile assets. Verify the returned stablecoin pay amount before saving the deposit. Show the exact transfer amount, asset, network, configured account minimum, method-specific technical minimum, confirmation guidance, and separate wallet gas warning. Keep processing fees off the member's credited USDT amount. Use generic labels and errors on customer and admin deposit screens while retaining provider identifiers in backend processing. Manual crypto approval is separate from ordinary XOF/manual-deposit approval: admin-only, pending/processing/review USDT provider deposits only, require a verified on-chain transaction reference and explicit confirmation, store the reference with a uniqueness constraint, perform a status-conditional atomic credit to `balanceUsdt` with a USDT transaction/audit record, and never let the ordinary XOF approval path credit provider deposits.
